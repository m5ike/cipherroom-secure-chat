M5cet 3.0

Šifrovaná komunikace peer-to-peer v prohlížeči: zprávy, soubory, hovory a sdílení polohy mezi lidmi, kteří znají společné heslo místnosti. Server zprostředkuje spojení, podrží zprávy pro nepřítomné a nikdy nevidí obsah.

Tato dokumentace popisuje verzi 3.0.0: nový signalizační protokol v2, šifrování v2 s identitou zařízení, spolehlivou frontu zpráv, novou administraci s živým sledováním provozu a auditem.

Node.js 24TypeScript 7React 19WebRTC DataChannelAES-GCM 256ECDSA P-256WebAuthn + PRFSQLite + SQLCipher

Pro koho je co

Uživatel — režimy, co šifrování chrání. Vývojář — architektura, protokol v2, API. Provozovatel — nasazení, administrace, audit, bezpečnost.

Co je nového ve 3.0

Validované rámce a limity, pseudonymy účtů, zapečetěná signalizace (ochrana hovorů před serverem), podepsané zprávy a soubory, fronta s lease a dead-letter, konzole s živým provozem a auditem. Plný přehled v seznamu změn.

    Funkce v kostce

    Zprávy

    Místnost i soukromí příjemci, odpovědi, přeposílání, stav (odesláno → uloženo → doručeno → přečteno), zprávy klikací, mizející a zapečetěné vlastním kódem.

    Soubory

    Malé přímo ve zprávě, velké po kusech po DataChannelu; když P2P nejde, přes šifrovanou proxy serveru. Opakování ztracených kusů, ověření otisku celého souboru.

    Hovory a média

    Audio a video přes WebRTC; DTLS otisky chráněné zapečetěnou signalizací. Sdílení polohy, NFC, přepis řeči, AI asistent a telefonie jako volitelné moduly.

    Účty

    Passkey (WebAuthn) s rozšířením PRF: z něj se v prohlížeči odvodí klíč trezoru i klíč vlastní databáze. Server nezná žádný z nich.

    Architektura#

    Tři běžící části: prohlížeče (veškerá kryptografie), hlavní služba (Express + WebSocket, všechen živý stav) a admin služba (konzole a nástroje). Před nimi obvykle nginx.

    Signalizační protokol v2#

    Jeden WebSocket na /ws, rámce jako JSON objekty s polem type. Verze 2 přinesla přesnou validaci, limity, pseudonymy, rámec auth a zapečetěnou signalizaci.

    Životní cyklus spojení

    Co se stane s každým rámcem

    1. Velikost — nad 256 KB (MAX_FRAME_BYTES) knihovna ws spojení zavře kódem 1009.
    2. Parsování (parseFrame) do přesného tvaru: typy, délky, formát ID ([A-Za-z0-9_:.-]{1,96}), base64, počty. Neznámý typ → error {code:"unknown-type"}, špatný tvar → invalid-frame.
    3. Limit třídy — token bucket na socket. Při překročení rate-limited {frame, retryAfterMs}; 20 odmítnutí za minutu → zavření 1008.
    4. Akce a záznam do monitoru provozu (typ, bajty, spojení, peer, účet, hash místnosti, stav).

    Brána spojení (při upgradu): 30 nových spojení za minutu a 20 současně na adresu, 5 000 celkem. Adresa se bere z X-Forwarded-For jen od důvěryhodné proxy (TRUST_PROXY).     Peer ID, resume a pseudonymy

    • Server v hello navrhne ID; klient smí v join požádat o vlastní. Je-li v místnosti obsazené jiným živým socketem, dostane nové — převzetí cizího ID už není možné (dřív šlo odklonit cizí signalizaci).
    • joined.resume je jednorázové tajemství. Při novém připojení do stejné místnosti ho klient pošle spolu se svým ID; server porovná SHA-256 v konstantním čase, starý socket dostane replaced a ID přejde na nové spojení.
    • Členové s účtem se místnosti ukazují jako account = base64url(HMAC-SHA256(tajemství, místnost ‖ 0 ‖ ID účtu))[0..22]. Stejná osoba má v každé místnosti jiný odkaz. Pole accountId nese totéž (alias pro klienty 2.x).

    const ws = new WebSocket("wss://chat.example.com/ws");
let me = null;

  if (f.type === "joined") { me = f.peerId; /* uložit f.resume pro reconnect */ }
  if (f.type === "rate-limited") setTimeout(retry, f.retryAfterMs);

setInterval(() => ws.send(JSON.stringify({ type: "ping", t: Date.now() })), 25_000);

    Šifrování v2#

    Veškerá kryptografie běží v prohlížeči přes WebCrypto. Server dostává jen šifrové texty a metadata potřebná ke směrování.

    Hierarchie klíčů místnosti

    Svázání s kontextem (AAD)

    Identita zařízení, TOFU a bezpečnostní čísla

    • Každý profil prohlížeče má pár ECDSA P-256; soukromý klíč je neexportovatelný (umí podepsat, nejde přečíst ani kódem aplikace) a leží v IndexedDB m5cet-identity.
    • Trust on first use: první ověřený klíč pro jméno v místnosti se připne (m5cet:pins:v1). Zpráva pod stejným jménem s jiným klíčem se označí jiný klíč a zobrazí se varování; neplatný podpis neplatný; starší klient nepodepsáno.
    • Bezpečnostní číslo dvou lidí = 12 skupin po 5 číslicích ze SHA-512 (1 025 kol) seřazených veřejných klíčů — obě strany vidí totéž a mohou ho porovnat mimo aplikaci.
    • Otisk vlastního zařízení i ověření odesílatele ukazuje Informace o zprávě.

    Kontrola klíče a replay

    Po otevření DataChannelu si peeři pošlou {kind:"key-check", v:2, check}. Nesouhlasí-li, aplikace řekne „jiné heslo místnosti“ místo nečitelných zpráv. Hodnota je odvozená z tajemství místnosti a k útoku na heslo nedává víc než libovolný šifrový text. ID přijatých zpráv si klient pamatuje (20 000 posledních) a opakované zahodí.

    Soubory

    1. Odesílatel vytvoří transferId, odvodí klíč souboru (HKDF, salt = ID přenosu) a pošle zapečetěná, podepsaná metadata.
    2. Každý kus (32 KiB) šifruje s AAD chunk|přenos|seq|počet a zároveň počítá jeho SHA-256.
    3. Konec přenosu nese zapečetěné a podepsané { root, totalChunks, size }, kde root = SHA-256 zřetězených otisků kusů.
    4. Příjemce ověří: metadata před alokací (velikost, počet kusů ≤ 2 000 000, konzistence), každý kus proti AAD, na konci součet bajtů, root a shodu podpisu s metadaty. Ztracené kusy si vyžádá (file-need / proxy-need, max. 3 kola).
    5. Jméno souboru se očistí (bez cest a řídicích znaků, BiDi) a MIME typ se omezí na bezpečné (obrázky, audio, video, PDF, text). HTML nebo SVG přijde jako application/octet-stream — nikdy se nespustí jako stránka v originu aplikace.

    Zapečetěné zprávy

    Text zprávy se navíc šifruje kódem předaným mimo aplikaci. Ve 3.0: kód 12 znaků z 31znakové abecedy bez záměnných znaků (≈ 59 bitů, zobrazení XXXX-XXXX-XXXX), losování bez modulo biasu, PBKDF2 600 000 iterací, při zadání se ignoruje velikost písmen, mezery a pomlčky. Zprávy z 2.x (6 znaků, 150 000 iterací) jdou dál otevřít. Text ani kód zapečetěné zprávy se nikdy neukládají mimo prohlížeč.

    Fronta zpráv pro nepřítomné#

    Když člen s účtem (passkey) a zapnutým uchováním na serveru odejde nebo odloží stránku, zůstane v místnosti jako nepřítomný. Ostatní mu dál píší; server šifrovou obálku uloží, odpoví „uloženo“, probudí ho Web Push a po návratu mu vše předá — v pořadí a s potvrzením.

    Poctivé účtenky

    Server si ke každé relayované zprávě pamatuje (v paměti, až 50 000 zpráv / 30 dní) odesílatele a příjemce. receipt přijme jen od účtu, kterému zprávu doručil, a pošle ho jen jejímu odesílateli. Ve 2.x mohl kdokoli v místnosti označit cizí zprávu jako přečtenou a vložit položky do cizí schránky.

    Lokální fronta (light režim)

    Bez serveru čeká zpráva, pro kterou není otevřený kanál, v paměti prohlížeče — už zašifrovaná. Zkouší se při otevření kanálu, po návratu do okna a jednou za minutu (200 zpráv, 60 pokusů, 24 h, respektuje TTL). Protože peer ID je od 3.0 stabilní i po výpadku (resume), obálky ve frontě zůstávají platné.

    Účty a passkeys#

    Účet je passkey (WebAuthn) — žádné heslo. Server uloží jen veřejný klíč a počítadlo podpisů; bez rozšíření PRF účet nevznikne, protože z něj prohlížeč odvozuje klíče:

    • HKDF(PRF, "m5cet:profile:v1") → klíč trezoru (profil + historie chatu, zapečetěné před odesláním),
    • HKDF(PRF, "m5cet:userdb:v1") → klíč vlastní SQLCipher databáze; server ho drží jen v paměti, dokud je uživatel přihlášený.

├── m5cet.db         # globální: uživatelé, passkeys, index DB, logy, přenosy, audit, fronta
├── storage.key      # master klíč, 0600 (nebo STORAGE_MASTER_KEY / STORAGE_KEY_FILE)
└── db/
    ├── db-<id>.db   # účet — klíč z passkey (PRF), jen v paměti
    └── db-<id>.db   # relace — klíč zabalený master klíčem, TTL 24 h od posledního použití, max. 7 dní

    Limity

    Kvóta 64 MB na účet, 16 MB na relaci (zápis nad kvótou se vrátí); zpráva ≤ 256 KB; hodnota kv ≤ 4 MB; 30 nových relací za hodinu z jedné adresy, 5 000 živých celkem; nejvýš 200 otevřených databází (LRU).

    Povýšení relace na účet

    Po vytvoření passkey se data relace zkopírují do databáze účtu v jedné transakci (ATTACH s klíčem), počty se ověří před commitem; relace se smaže až potom.

    Klíče

    Klíč účtu drží server po držitelích (zařízeních); zapomene ho a přepíše nulami, až se odhlásí poslední, nebo po 12 h nečinnosti. ID relací jen jako HMAC.

    Veřejný status

    /api/storage/status říká jen available, engine, caller, locked — nic o ostatních uživatelích. Úplný stav je v administraci.

    Bezpečnost konzole

    • Token je jen v paměti záložky (volitelně v sessionStorage), nikdy v localStorage — starý klíč m5cet:admin:cfg konzole při načtení smaže.
    • CSP script-src 'self', žádné inline skripty ani eval, frame-ancestors 'none'. Vše ze serveru jde do stránky přes textContent.
    • Živý stream je Server-Sent Events čtený přes fetch() — token v hlavičce, ne v URL (nezůstane v logu proxy).
    • Odmítnuté tokeny se počítají: 30 za 15 minut na adresu. Každý zásah operátora se zapíše do auditu (kategorie admin).
    • Doporučeno omezit /console/, /admin/ a /api/admin/ v nginx na adresy správců (allow … ; deny all;).

    Upgrade z 2.x na 3.0

    1. git pull, npm ci, npm run build (nebo ./update.sh).
    2. Do nginx přidat blok /api/admin/; nginx -t && systemctl reload nginx.
    3. Běží-li hlavní služba jinde než na 127.0.0.1:$PORT, nastavit admin službě MAIN_URL.

    Bezpečnostní opatření serveru#

    HTTP

    Helmet, CSP v produkci script-src 'self' a object-src 'none'; Cache-Control: no-store všude; limity před parsery těl (veřejné API 100 / 15 min, trezor 300, úložiště 1 200, admin 30 odmítnutí / 15 min); JSON do 256 KB (trezor 8 MB, úložiště 12 MB); chyby 500 bez interních detailů.

    Logy

    Řádek požadavku = metoda, cesta, stav, doba, velikost. Nikdy těla — odpovědi nesou session tokeny a šifrové texty (2.x je logovala). Surové tělo se drží jen pro webhooky poskytovatelů kvůli podpisům.

    WebSocket

    Origin, brána spojení, maxPayload 256 KB, validace rámců, limity tříd, vyhazování opakovaných narušitelů, heartbeat, zpětný tlak, vlastnictví přenosů, rozesílání jen ověřených polí.

    Identita a soukromí

    Pseudonymy účtů v místnosti, obecná odmítnutí relay, IP v monitoru zkrácené na /24 (/48), místnosti jako hash, audit komunikace jen na vyžádání, zapečetěné detaily v databázi.

    SSRF

    Server POSTuje jen na push endpointy známých služeb (https, bez portu a přihlašovacích údajů); příkaz ke stažení souboru přijme jen https adresu a klient se uživatele zeptá.

    Ukončení

    SIGTERM/SIGINT: sockety se zavřou (klienti se vrátí přes resume), účty se zapíšou, databáze se zavřou a klíče vynulují, pak konec (nejpozději za 8 s).

    Změny ve 3.0.0#

    Přidáno

    Protokol v2 (validace, limity, brána, Origin, resume, pseudonymy, auth, odvolání, heartbeat, zpětný tlak), šifrování v2 (klíče podle účelu, AAD, zapečetěná signalizace, podpisy, TOFU, ověřené soubory), SQLite fronta s lease a dead-letter, nová konzole s živým provozem, auditem, uživateli, frontou, úložištěm a systémem, dokumentace HTML + PDF.

    Opraveno

    XSS přes MIME souboru, DoS přes metadata souboru, převzetí peer ID, podvržené účtenky a položky schránky, logování session tokenů, SSRF přes push endpoint, token admina v localStorage, příkazy z admin služby, které nikdy nedorazily, vlastní zprávy po obnovení označené jako cizí, 18 oprav úložiště.

    Změněno

    Veřejný status úložiště bez statistik ostatních, metadata endpointy jen s tokenem, kód zapečetěné zprávy 12 znaků, transfer log bez jmen souborů, historie serveru bez passkey šifrovaná v prohlížeči.

    Nekompatibilní

    Klienti 2.x se s 3.0 nespojí (nezapečetěná signalizace) a nepřečtou obálky v2. Po nasazení obnovit všechna okna; přidat blok nginx /api/admin/.

    Podrobný seznam: CHANGELOG.md. Tato dokumentace odpovídá kódu verze 3.0.0.
