    Funkce v kostce

    Zprávy

    Místnost i soukromí příjemci, odpovědi, přeposílání, stav (odesláno → uloženo → doručeno → přečteno), zprávy klikací, mizející a zapečetěné vlastním kódem.

    Soubory

    Malé přímo ve zprávě, velké po kusech po DataChannelu; když P2P nejde, přes šifrovanou proxy serveru. Opakování ztracených kusů, ověření otisku celého souboru.

    Hovory a média

    Audio a video přes WebRTC; DTLS otisky chráněné zapečetěnou signalizací a každý rámec navíc šifrovaný klíčem páru (E2EE hovorů). Sdílení polohy, NFC, přepis řeči, AI asistent a telefonie jako volitelné moduly.

    Účty

    Passkey (WebAuthn) s rozšířením PRF: z něj se v prohlížeči odvodí klíč trezoru i klíč vlastní databáze. Server nezná žádný z nich. Více passkeys a obnovovací kód pro případ ztráty zařízení.

    Architektura#

    Tři běžící části: prohlížeče (veškerá kryptografie), hlavní služba (Express + WebSocket, všechen živý stav) a admin služba (konzole a nástroje). Před nimi obvykle nginx.

    Signalizační protokol v2#

    Jeden WebSocket na /ws, rámce jako JSON objekty s polem type. Verze 2 přinesla přesnou validaci, limity, pseudonymy, rámec auth a zapečetěnou signalizaci.

    Životní cyklus spojení

    Co se stane s každým rámcem

    1. Velikost — nad 256 KB (MAX_FRAME_BYTES) knihovna ws spojení zavře kódem 1009.
    2. Parsování (parseFrame) do přesného tvaru: typy, délky, formát ID ([A-Za-z0-9_:.-]{1,96}), base64, počty. Neznámý typ → error {code:"unknown-type"}, špatný tvar → invalid-frame.
    3. Limit třídy — token bucket na socket. Při překročení rate-limited {frame, retryAfterMs}; 20 odmítnutí za minutu → zavření 1008.
    4. Akce a záznam do monitoru provozu (typ, bajty, spojení, peer, účet, hash místnosti, stav).

    Peer ID, resume a pseudonymy

    • Server v hello navrhne ID; klient smí v join požádat o vlastní. Je-li v místnosti obsazené jiným živým socketem, dostane nové — převzetí cizího ID už není možné (dřív šlo odklonit cizí signalizaci).
    • joined.resume je jednorázové tajemství. Při novém připojení do stejné místnosti ho klient pošle spolu se svým ID; server porovná SHA-256 v konstantním čase, starý socket dostane replaced a ID přejde na nové spojení.
    • Členové s účtem se místnosti ukazují jako account = base64url(HMAC-SHA256(tajemství, místnost ‖ 0 ‖ ID účtu))[0..22]. Stejná osoba má v každé místnosti jiný odkaz. Pole accountId nese totéž (alias pro klienty 2.x).

    Šifrování v2#

    Veškerá kryptografie běží v prohlížeči přes WebCrypto. Server dostává jen šifrové texty a metadata potřebná ke směrování.

    Identita zařízení, TOFU a bezpečnostní čísla

    • Každý profil prohlížeče má pár ECDSA P-256; soukromý klíč je neexportovatelný (umí podepsat, nejde přečíst ani kódem aplikace) a leží v IndexedDB m5cet-identity.
    • Trust on first use: první ověřený klíč pro jméno v místnosti se připne (m5cet:pins:v1). Zpráva pod stejným jménem s jiným klíčem se označí jiný klíč a zobrazí se varování; neplatný podpis neplatný; starší klient nepodepsáno.
    • Bezpečnostní číslo dvou lidí = 12 skupin po 5 číslicích ze SHA-512 (1 025 kol) seřazených veřejných klíčů — obě strany vidí totéž a mohou ho porovnat mimo aplikaci.
    • Otisk vlastního zařízení i ověření odesílatele ukazuje Informace o zprávě.

    Kontrola klíče a replay

    Po otevření DataChannelu si peeři pošlou {kind:"key-check", v:2, check}. Nesouhlasí-li, aplikace řekne „jiné heslo místnosti“ místo nečitelných zpráv. Hodnota je odvozená z tajemství místnosti a k útoku na heslo nedává víc než libovolný šifrový text. ID přijatých zpráv si klient pamatuje (20 000 posledních) a opakované zahodí.

    Soubory

    1. Odesílatel vytvoří transferId, odvodí klíč souboru (HKDF, salt = ID přenosu) a pošle zapečetěná, podepsaná metadata.
    2. Každý kus (32 KiB) šifruje s AAD chunk|přenos|seq|počet a zároveň počítá jeho SHA-256.
    3. Konec přenosu nese zapečetěné a podepsané { root, totalChunks, size }, kde root = SHA-256 zřetězených otisků kusů.
    4. Příjemce ověří: metadata před alokací (velikost, počet kusů ≤ 2 000 000, konzistence), každý kus proti AAD, na konci součet bajtů, root a shodu podpisu s metadaty. Ztracené kusy si vyžádá (file-need / proxy-need, max. 3 kola).
    5. Jméno souboru se očistí (bez cest a řídicích znaků, BiDi) a MIME typ se omezí na bezpečné (obrázky, audio, video, PDF, text). HTML nebo SVG přijde jako application/octet-stream — nikdy se nespustí jako stránka v originu aplikace.

    Zapečetěné zprávy

    Text zprávy se navíc šifruje kódem předaným mimo aplikaci. Ve 3.0: kód 12 znaků z 31znakové abecedy bez záměnných znaků (≈ 59 bitů, zobrazení XXXX-XXXX-XXXX), losování bez modulo biasu, PBKDF2 600 000 iterací, při zadání se ignoruje velikost písmen, mezery a pomlčky. Zprávy z 2.x (6 znaků, 150 000 iterací) jdou dál otevřít. Text ani kód zapečetěné zprávy se nikdy neukládají mimo prohlížeč.

    Šifrování v3 3.1#

    Verze 3.1 mění první krok (Argon2id), skrývá před serverem název místnosti a živé zprávy už nešifruje sdíleným klíčem místnosti, ale klíči odesílatelů s ratchetem a párovými klíči. Vše z kapitoly Šifrování v2 (AAD, podpisy, ověřené soubory) platí dál.

    Argon2id ve Web Workeru

    PBKDF2 ztěžuje hádání hesla jen časem; grafická karta ho spočítá paralelně. Argon2id (64 MiB paměti, 3 průchody, hash-wasm) stojí útočníka paměť na každý pokus. Výpočet běží v kdf.worker.ts, stránka nezamrzne; kde worker nejde spustit, poběží v hlavním vlákně. WebAssembly potřebuje v CSP 'wasm-unsafe-eval' (nic jiného se nepovoluje). Obálky v2 (PBKDF2, např. zprávy čekající ve frontě z 3.0) se otevřou klíči odvozenými při první potřebě.

    Identita účtu a bezpečnostní čísla

    Relay souborů, když P2P nejde

    Za striktním NAT bez TURN se DataChannel neotevře. Aplikace pak pošle soubor šifrovaně přes server (proxy transport) — dřív přenos rovnou odmítla. Server kusy jen předává (žádná kopie v paměti), hlídá vlastnictví přenosu a strop 64 souběžných přenosů. Odesílatel se řídí rozpočtem, který server ohlásí (2 MiB/s, 60 rámců/s na socket, s rezervou): posílá na 80 %, polovinu burstu, a čeká, dokud vlastní buffer socketu neklesne pod 1 MiB. Relay tak kus nikdy neodmítne ani spojení neodpojí.

    Fronta zpráv pro nepřítomné#

    Účty a passkeys#

    Účet je passkey (WebAuthn) — žádné heslo. Server uloží jen veřejné klíče a počítadla podpisů; bez rozšíření PRF účet nevznikne, protože z něj prohlížeč odvozuje kořen účtu a z něj klíče:

    • HKDF(kořen, "m5cet:profile:v1") → klíč trezoru (profil + historie chatu, zapečetěné před odesláním),
    • HKDF(kořen, "m5cet:userdb:v1") → klíč vlastní SQLCipher databáze; server ho drží jen v paměti, dokud je uživatel přihlášený,
    • HKDF(kořen, "m5cet:account-sign:v1") → podpisový klíč účtu Ed25519 (identita účtu).

    Po vytvoření passkey se data relace zkopírují do databáze účtu v jedné transakci (ATTACH s klíčem), počty se ověří před commitem; relace se smaže až potom.

    Klíč účtu drží server po držitelích (zařízeních); zapomene ho a přepíše nulami, až se odhlásí poslední, nebo po 12 h nečinnosti. ID relací jen jako HMAC.

    Veřejný status

    /api/storage/status říká jen available, engine, caller, locked — nic o ostatních uživatelích. Úplný stav je v administraci.

    Kde a jak se ukládají

    Seznam, nastavení, statistiky i log tvoří jeden objekt, který prohlížeč zapečetí klíčem trezoru účtu (AES-GCM, klíč z PRF passkey, stejně jako profil) a uloží jako třetí část trezoru: PUT /api/account/vault s { connections: { ct, count } }. Server drží jen šifrovaný blok (nejvýš 1,5 MB), jeho velikost, čas a počet připojení — nikdy klíč, název místnosti ani to, kdo se kam připojil. Úprava se uloží hned; počítadla (zprávy, obnovy) se sbírají a odejdou nejdéle za 8 s, nebo když se stránka skryje či uživatel odhlásí. Dokud se trezor nenačte, klient nic nezapíše (starší zařízení tak nepřepíše novější data).

    Sdílet připojení 3.3

    V Moje připojení má každý záznam mezi hvězdičkou a košem tlačítko Sdílet. Otevře okno Sdílet připojení se stejnou pozvánkou jako okno Místnost — room ID a klíč zapečetěné 12místným kódem, omezený počet použití a platnost (1 h / 24 h / 7 d) — upravenou pro tuto situaci:

    • Není potřeba být připojený — klíč je uložený v připojení.
    • Karta připojení nahoře (barva, název, místnost, server) a volby jako řada tlačítek místo rozbalovacích seznamů.
    • Jméno pro pozvaného (jinak náhodné, např. bystry-sokol-42).
    • Používá-li připojení jiný signalizační server, pozvánka ho nese (zapečetěný s klíčem) a pozvaný se připojí tam — jen pokud ho správce tohoto serveru povoluje (Client & addons). Adresa, která není čisté wss://, pozvánku zneplatní.
    • Výsledek: odkaz, kód, sdílení přes aplikace, QR, nový odkaz, zneplatnění, Hotovo.

    Jiný obslužný server

    Připojení může místo tohoto serveru použít jiný signalizační server M5cet: ze seznamu, který správce vede v konzoli, nebo — když to dovolí — libovolnou adresu wss:// (ws:// jen pro localhost; bez přihlašovacích údajů, dotazu a fragmentu). Tamní provozovatel musí mít tuto doménu v ALLOWED_ORIGINS. Na cizí server klient neposílá token účtu, neotevírá úložiště přes WebSocket, nevyužívá relay pro nepřítomné a neposlouchá tamní administrátorské příkazy. Šifrování je stejné — klíč místnosti prohlížeč neopustí nikdy. Od 3.3 si relace pamatuje i server a uložené připojení, takže obnovení stránky vrátí spojení na tentýž server (dříve na tento).

    • Pod náhledem je souhrn Accessibility a čipy u prvků ve stromu.     Výkon

    Šablony ({$x|filtr}, podmínky, výrazy) se překládají na funkce jednou a pak se jen volají; strom rozvržení se také přeloží jednou (pro každý uzel připravené čtení dat, atributy, podmínky a opakování), neměnné části se vytvoří jednou a React je při dalším vykreslení přeskočí. Nová syntaxe: filtry nad výrazem v závorce, např. {=('acc.signedInAs'|t|replace:'{name}':$userName)}.

    Bezpečnost: server i aplikace validují strom týmž modulem (layout-tree.ts) — jen známé prvky a tagy, žádné on* atributy, style, srcdoc ani formaction, adresy jen https:, cesty webu, #, mailto:, tel: a data:image (při vykreslení i data:/blob: z dat aplikace, nikdy javascript:), CSS bez url() a výrazů, limity velikosti. Vykreslení nikdy nepoužívá innerHTML; prvek HTML jde přes bezpečný parser. Konzole a náhled si píší jen se stejným původem.

    Podpis zpráv

    S CLUSTER_SECRET nese každá zpráva HMAC-SHA256; nepodepsané a padělané se zahodí (počítadlo dropped). Kdo smí do Redisu publikovat, bez tajemství místnosti neovládne. Bez tajemství server při startu varuje.

    Sdílená data

    Instance sdílejí DATA_DIR (jeden hostitel nebo sdílený svazek): SQLite úložiště a fronta jsou bezpečné pro více procesů (WAL), účty jsou JSON — instance si před každou operací načte, co zapsala jiná, a zapisuje hned.

    Redis klient

    Vlastní RESP klient bez závislostí: redis:// i rediss:// (TLS), AUTH, SELECT, reconnect s backoffem, znovu-přihlášení k odběru; zprávy odeslané při výpadku se po návratu odešlou (max. 1 000).

    Limity spojení a rámců jsou na instanci. Dvě instance měnící tentýž účet ve stejné milisekundě mohou jednu změnu ztratit — sticky sessions to prakticky vyloučí.

    Bezpečnostní opatření serveru#

    HTTP

    Helmet, CSP v produkci script-src 'self' 'wasm-unsafe-eval' (jen WebAssembly pro Argon2id, žádný eval) a object-src 'none', workery jen z vlastního originu; Cache-Control: no-store všude; limity před parsery těl (veřejné API 100 / 15 min, trezor 300, úložiště 1 200, admin 30 odmítnutí / 15 min); JSON do 256 KB (trezor 8 MB, úložiště 12 MB); chyby 500 bez interních detailů.

    Logy

    Řádek požadavku = metoda, cesta, stav, doba, velikost. Nikdy těla — odpovědi nesou session tokeny a šifrové texty (2.x je logovala). Surové tělo se drží jen pro webhooky poskytovatelů kvůli podpisům.

    WebSocket

    Origin, brána spojení, maxPayload 256 KB, validace rámců, limity tříd, vyhazování opakovaných narušitelů, heartbeat, zpětný tlak, vlastnictví přenosů, rozesílání jen ověřených polí.

    Identita a soukromí

    Pseudonymy účtů v místnosti, obecná odmítnutí relay, IP v monitoru zkrácené na /24 (/48), místnosti jako hash, audit komunikace jen na vyžádání, zapečetěné detaily v databázi.

    SSRF

    Server POSTuje jen na push endpointy známých služeb (https, bez portu a přihlašovacích údajů); příkaz ke stažení souboru přijme jen https adresu a klient se uživatele zeptá.

    Ukončení

    SIGTERM/SIGINT: sockety se zavřou (klienti se vrátí přes resume), účty se zapíšou, databáze se zavřou a klíče vynulují, pak konec (nejpozději za 8 s).

    Změny ve 3.1.0#

    Přidáno
